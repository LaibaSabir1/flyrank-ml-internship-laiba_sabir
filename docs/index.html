Which page should we fix first?

A ranked, evidence-backed content-refresh priority queue for a fixed weekly review capacity

FlyRank ML Internship 2026 · Content Refresh / Page Review Priority lane · anonymized data

Abstract

Given a reviewer with capacity for roughly 50 pages a week against an inventory of about 30,000, which pages should they open first? This project builds a transparent baseline rule, then a learned ranking model, on FlyRank's anonymized content-performance dataset (30,000 pages, 32 clients). Under a client-holdout split — no client's pages appear in both train and test — the best model reaches Precision@50 of 0.72 versus 0.32 for the hand-written rule, a 2.2× lift. A naive split on the same data inflates that number to 0.90 — a gap of 0.18 that exists purely as a validation artifact, not model skill. The output is a ranked, reason-coded action queue intended as decision support for a human reviewer, not an automatic publishing decision.

1. Introduction / Problem

Content that ranks well in search quietly decays: rankings slip, clicks drop, and most teams notice too late. FlyRank's product already flags pages today with hand-written rules (a health score, quick-win tags) — useful, but rules run out where signals get numerous, tangled, and shifting. The decision this project improves is narrow and concrete: out of thousands of pages, which one should a human look at first, this week, given a fixed review budget? A wrong call in either direction has a real cost — a false positive near the top wastes a reviewer's limited hour; a false negative lets a genuinely declining, high-traffic page keep losing visibility unnoticed.

2. Data

The primary dataset is FlyRank's anonymized starter export: 30,000 content pages across 32 pseudonymized clients, with trailing-90-day search and engagement metrics. No client names, domains, URLs, page titles, or raw keywords are present in the data or anywhere in this write-up. The label — is_declining_label — marks a page as declining when last-30-day search impressions fell more than 20% versus the prior 30 days (declining-label rate: 0.542). This is a current-window proxy, not a future outcome; see Limitations.

Excluded by design: pseudonymous content_id/client_id (grouping only), trend_direction/trend_pct (the label is derived from these — see the leakage check in Methodology), and FlyRank's own product decision flags (health_score, priority_score, and similar), which were never shipped in this dataset in the first place. A parallel, larger warehouse release (~79M rows across ~70 clients) backs the project's earlier validation work at a larger scale; this paper's headline numbers are computed on the 30k-row slice for reproducibility from a public repo alone.

3. Methodology

Baseline. A transparent, human-readable rule combining visibility, staleness, position opportunity, and content depth — no fitted weights, every term a percentile rank of an observable signal.

Model. A small model comparison (logistic regression, decision tree, random forest) over 18 numeric and 8 categorical observable features (search demand, engagement, position, age/freshness/depth tiers). Product decision flags and label-derived columns are excluded from the feature set entirely.

Leakage check. Fitting the same model with trend_pct included pushes in-sample Precision@50 from 0.94 to 1.00 — a confession, not a result. trend_pct is excluded from every reported model.

Validation design. A client-holdout split (~20% of clients held out entirely, GroupShuffleSplit on client_id) is the split of record. A naive stratified row split is reported alongside it, purely as an honesty check on how much a careless split would have flattered the result.

5. Limitations & honest framing

  • The label is a current-window proxy, not a validated future outcome. A stronger version predicts a future 30-day window from a strictly prior feature window.
  • Staleness is a weak-to-reversed signal across every audit run so far — stale pages decline less often, not more. "Just refresh old pages" is not, by itself, a defensible strategy from this data.
  • This is one run, on one 30,000-row anonymized slice, with fixed random seeds — not a benchmark on the full ~79M-row warehouse.
  • No causal claim is made. Nothing here shows a refresh causes recovery; that requires an experiment this data cannot provide.
  • The split generalizes across clients, not across time — it does not test whether the ranking still works next quarter.

7. Reproducibility

Every number and chart on this page is generated by work/notebooks/capstone.ipynb, executed top to bottom with fixed random seeds (random_state=42). The full repo, including the weekly lane notebooks this capstone builds on (research question through validation audit), is public at github.com/LaibaSabir1/flyrank-ml-internship-laiba_sabir. Re-run instructions: clone the repo, pip install -r requirements.txt, open work/notebooks/capstone.ipynb, Runtime → Run all.
